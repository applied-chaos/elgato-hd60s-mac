# Elgato HD60 S (0fd9:0074) USB protocol

Recovered statically from Elgato Game Capture HD 2.11.14 for macOS
(`Game_Capture_HD_2.11.14.zip`, sha256 `e00efce3…c1ba74`). Nothing was run and no command was sent to the device.

- `Contents/Frameworks/libUB530.dylib` (sha256 `8a5c35d4…6d3e`, x86_64): the whole HD60 S device driver. It was licensed from YUAN High-Tech: the code also matches VID 0x1164 / PID 0x053x and 0x05ca:0x0901. It talks to the device only through an app-supplied `UB530_Transport` interface.
- `Contents/MacOS/Game Capture HD`: implements `UB530_Transport` as `BeddoRTUSBInterface` (IOKit) and runs the bulk/isoch readers (`CUSBMultiReaderBulkBeddoRT`, `CUSBMultiReaderIsochBeddoRT`).
- `BeddoLibrary.dylib` covers the older HD60 and Game Capture HD (Fujitsu chips). It is **not** used for the HD60 S.

Addresses below are `libUB530.dylib` file/VM offsets unless prefixed `app:`. Full Ghidra output is in `docs/re/libUB530_ghidra.c`, generated by `docs/re/DumpAll.java`. It is derived from Elgato's binary, so keep it private.

## 1. Device matching and firmware

**The app remaps IDs before handing them to the library** (app:0x100344dd0–0x100344e4e, `BeddoRTBoard` ctor):

```
if vid == 0x0fd9 && pid in {0x4f, 0x5e, 0x74}:  vid, pid = 0x1164, 0xf535
else (e.g. 0fd9:0076):                          passed unchanged
UB530_Public(transport, vid, pid)
```

So **our 0x74 runs as 1164:f535** inside libUB530. Every `pid & 0xfff` test sees **0x535**.

`UB530_Public::UB530_Public` @0x24834 then picks the class:
- PID 0x76 uses vtable 0x2bfa8 (ctor 0x17e02), an IT680x-based board (VSTATE_* strings) with a GPIO helper at 0xca8/0xd06.
- Everything else, including 0x74→f535, uses vtable 0x2bce0 (ctor 0x8bb2): the MST3367 board.

The x535 branches that **do apply to our unit**:
- `FUN_d118` jumps to LAB_d2f8 and runs `FUN_1c910` (GPIO power-up + MCU bridge probe), then `FUN_1d02e` (Rx init).
- `FUN_c8d2` also runs `FUN_1d02e`.
- `FUN_a1d0` returns true.

When the probe in `FUN_1c910` answers, `dev+0xac = 1`. **From then on every I2C access goes through the MCU bridge (`FUN_1c746`), not plain 0xC0**; see §2. That is why a plain `0xC0` read with wValue=addr returns a stale EP0 buffer.

The app picks firmware by `vendorID == 0x0fd9 && productID == 0x76` (app:0x10039b1aa). That match means BeddoRTv4 (`ub530_v200819`). Anything else, **including 0x74**, means BeddoRT (`ub530_v170317`). bcdDevice is not consulted.

Firmware:
- `Firmware/BeddoRT/ub530_v170317.bin` and `Firmware/BeddoRTv4/ub530_v200819.bin` are Cortex-M images for the Nuvoton MCU (vector table: SP 0x20000d70).
- The path builder is app:0x10039b016 (v4 → "200819"). Upload happens only via `UB530_Public::UpdateMCUFirmware` → vtable+0xa0 → `FUN_177c8`, which reads the file and size-checks it (≤0x8000).
- **No firmware upload happens at plug-in.** The device boots its FX3 firmware from SPI flash.
- EDID read/write (`FUN_17990`/`FUN_1796a`) goes through a flash/MCU helper at `dev+0x41a8`, so it is also a flash write.

**A driver must never call the firmware-update or EDID-write paths.**

## 2. Transport and control primitives

### UB530_Transport vtable (lib calls → app `BeddoRTUSBInterface` vtable app:0x100726208)

| slot | lib wrapper | app impl | meaning |
|---|---|---|---|
| +0x00 | FUN_175cc | app:0x100344aa2 | `Control(bRequest, wIndex, wValue, buf, wLength, isOut, &done)` |
| +0x08 | FUN_1757a | app:0x100344bb8 | stop interrupt read (abort pipe) |
| +0x10 | FUN_1758c | app:0x100344b68 | arm async 1-byte read on interrupt EP 0x81 |
| +0x18 | FUN_17564 | app:0x100344c18 | armed and **not yet fired** |
| +0x20 | FUN_1754e | app:0x100344c0e | armed |
| +0x28 | – | app:0x100344cf6 | start "BeddoRT_Interrupt" thread |
| +0x30 | FUN_175ba | app:0x100344d2e | stop that thread |

The app's control implementation is app:0x100344aa2, verified in assembly. It builds an `IOUSBDevRequestTO` and calls `ControlRequestTO(pipe 0)` at interface vtable +0x128:

| struct field | value |
|---|---|
| +0 `bmRequestType` | `(~isOut<<7) \| 0x40`, i.e. 0x40 OUT / 0xC0 IN |
| +1 `bRequest` | arg (sil) |
| +2 `wValue` | arg in rcx |
| +4 `wIndex` | arg in rdx |
| +6 `wLength` | arg (r9w) |
| timeouts | 3000 ms no-data, 2000 ms completion |

The lib wrapper `FUN_175cc(dev, req, A, B, buf, len, dirIn)` swaps registers (A→rcx, B→rdx). So **wValue = A and wIndex = B**, with no byte-swapping.

- Success means IOReturn ≥ 0. The bytes-done count is ignored, so a short or stale IN can't be detected.
- There is no write-then-read inside the transport: any two-step sequence happens one layer up (§2 bridge).

### Vendor requests (census of every `FUN_175cc` call site)

| bRequest | dir | wValue | wIndex | data | use |
|---|---|---|---|---|---|
| 0xC0 | OUT/IN | 8-bit I2C addr | sub-address | bytes | direct I2C, only when `dev+0xac==0`. **Not used on 0x74**: it returns a stale buffer |
| 0xC0 | OUT | `0x5000 \| target` | 0 | bytes | **MCU bridge write** (`FUN_9b7a`) |
| 0xC0 | IN | `0x5000 \| target` | 0 | n | **MCU bridge read** (`FUN_9bcf`) |

| 0xC2 | OUT | x | 0 | – | `FUN_a601`; init sends wValue=0 |
| 0xC2 | IN | 0 | 0 | 1 | status byte (probe on 05ca:0901 / x531 only) |
| 0xC3 | – | – | – | – | PID x530 only (not HD60 S) |
| 0xC5 | OUT | period | `type \| (0xac<<8)` | 4-byte entries | upload I2C replay program, transformed format (unused on HD60 S) |
| 0xC6 | OUT | period (ms) | `type \| (0xac<<8)` | 4-byte entries | upload I2C replay program, raw. **len 0 = disable** |

### MCU I2C bridge (`FUN_1c746(dev, addr, wlen, wdata, rlen, rbuf)`, used when `dev+0xac==1`, i.e. on 0x74)

The Nuvoton MCU owns the board I2C bus. The bridge uses the "0x66" proxy target, so wValue = 0x5066.

- **Read** (rlen > 0):
  1. OUT `wValue=0x5066`, data `[addr|1, rlen, wdata…]`
  2. IN `wValue=0x5066`, `rlen` bytes
- **Write** to addr ∈ {0x88, 0x98, 0x9C}: OUT `wValue=0x5000|addr`, data `wdata` (= `[sub, val…]`).
- **Write** to any other addr: OUT `wValue=0x5066`, data `[addr, wdata…]`.
- Register read `FUN_9da7` = bridge read with `wdata=[sub]`. Register write `FUN_9cfa` = bridge write with `wdata=[sub, val…]`.
- MST3367 bank access is unchanged on top of this: write `[0x00, bank]` to 0x9C, then read or write `reg`.
- MCU commands go to addr 0xAA, e.g. `[12 34 57]` (status probe), `[12 34 58]` (version), `[12 34 60]` (MCU reset, `FUN_1c8d2`). On the wire that is `AB 03 12 34 5x`, which matches the `AB 03 12` Windows traces.

### I2C devices (8-bit addresses)

| addr | device | access |
|---|---|---|
| 0x9C | MStar MST3367 HDMI receiver, banked | `ReadReg(bank,reg)` @0xb9f4 = I2C write [bank] to sub 0x00, then I2C read sub=reg. `WriteReg` @0xb98e = write [bank]→sub 0, then [val]→sub reg |
| 0x9A | ITE IT66121 HDMI transmitter (HDMI out), see §6 | `FUN_bafa`/`FUN_bad2` read/write one register, `FUN_babb`/`FUN_baa4` bursts. Reg 0x09 ≠ 0xB2 → transmitter lost its init; reg 0x0E bit7 = transmitter interrupt pending |
| 0x94 | audio codec/volume (`FUN_1ce18`, `FUN_1caf4`) | regs 3,4,7,9,0x0a–0x11 |
| 0x98 | board control/MCU | reg 0x20: bit6 = SD (240/288-line) mode, written 5 at init (HD60 S); reg 0x00/0xF0 on other boards |
| 0xAA | MCU commands | see the bridge above |
| 0xD4 | audio device with 16-bit register addresses, probably a sample-rate converter (§6.8) | write `[00 reg val]`; read `[00 reg]` → 2 bytes, value in the second |
| 0x88 | analogue decoder | internal inputs 5/6 only; unused on HD60 S |

## 3. Sequences (PID 0x74)

`UB530_Public` vtable 0x2bce0: +0x18 Initialize=0x8c80, +0x20 Uninitialize=0x8cae, +0x28 Reset=0xe56e, +0x30 DetectVideoFormat=0x90bc, +0x38 SetupForVideoFormatScanning=0x90a4, +0x40 AudioRate=0x9184, +0x98 FirmwareName=0x8dbe, +0xa8/+0xb0 EDID W/R, +0xc8/+0xd0 MST3367 W/R=0x9a36/0x9a7a, +0xd8 SetInput=0x8ce2.

### Host side (app)
1. Open the device and set configuration 1.
2. Claim iface 0 (video) and iface 1 (interrupt).
3. Choose the transfer mode. The default pref `BeddoRTUseBulk=true` (EGCInitialDefaults.plist) means **iface 0 alt 4, bulk EP 0x83**. Isochronous is alt 1–3 on EP 0x83, with 4 read buffers × 160 × bytes-per-interval.
4. Construct `UB530_Public(transport, 0x0fd9, 0x0074)`, call `CreateContext(...)`, then `Initialize()`.
5. Continuously read EP 0x83 and feed the concatenated payload to `ParseInput`.
6. Poll `DetectVideoFormat()`.

### Initialize = FUN_d118 then FUN_cc7e(dev, -1)
`FUN_d118`, as seen by the lib (id 1164:f535):
1. `0xEC` OUT, 10 bytes `b8 22 00 00 00 c0 00 00 00 ca`. Gaps were unset in Elgato's code; zeros proposed.
2. `0xC2` OUT wValue=0.
3. `0xC7` OUT wValue=100.
4. **`FUN_1c910`, power-up and MCU bridge:**
   1. `0xC1` OUT wValue=`0xC039` (GPIO 57 → input).
   2. `0xC1` OUT wValue=`0x4134` (GPIO 52 → output high: MCU/Rx enable).
   3. Every 10 ms, at most 100×: `0xC1` IN wValue=`0x0039` len 1, until it reads `0x01` (MCU ready).
   4. Up to 200×: bridge read addr 0xAA, wdata `[12 34 57]`, rlen 3. That is OUT 0x5066 `AB 03 12 34 57`, then IN 0x5066 ×3.
      - `51 10 xx` ('Q',0x10): bridge OK, set `dev+0xac=1`. Then the same read with `[12 34 58]` gives the firmware version, stored as `b0<<16|b1<<8|b2` at `dev+0xc0`.
      - `33 44 55` ('3','D','U'): MCU busy. Sleep 100 ms and retry.
      - Anything else: no bridge, `dev+0xac=0`.
5. **`FUN_1d02e`, Rx init:**
   1. Read 0x9A regs 1, 2, 3, 5.
   2. Run `FUN_1db0a` and `FUN_20a4e` (MST3367 init, once).
   3. `FUN_1d10a(rx, 0x44)`.
6. `0xC6` OUT wValue=0 wIndex=0 len=0. This probes support and disables any replay program.
7. `FUN_c8d2(dev, input, -, audio, -, 0)`, which:
   - selects the HDMI input (`FUN_10e8a`, MST3367 setup);
   - calls `FUN_1ce00` (audio source);
   - writes I2C 0x98 reg 0x20 = 0x05.

`FUN_cc7e` (start):
1. `FUN_1d10a(rx, 0x44)` resets the Rx state machine (0x44 = "no mode").
2. MST3367 writes: `b0:0xAB |= 0x80`; `b2:0x27 = 0xFF`; `b0:0xB3 = 0xFF`; `b1:0x24 = 0x41`; `b1:0x25 = 0`; `b1:0x26 = 0`; `b1:0x27 = 0` ×5. Then restore 0xAB (bit7 clear) and `b2:0x27`, and set `b0:0xB3 = 0`.
3. Poll `b2:0x0E & 7` (10 × 5 ms), then write-back-to-clear `b2:0x0E` until `&7 == 0` (≤500 × 5 ms).
4. `FUN_10b6b`: colour-space conversion. `b0:0x90 = 0x15`, `0x91 = 0x15`, `0x92 = mode` (0x40 or 0x62), `0x93..0xAA` = 12 big-endian s16 coefficients (BT.601 for 640/720/768 widths, else BT.709; scaled 0xDC0/0x1000 for limited range). Then `b0:0xB0 = (b0:0xB0 & 0xC2) | 0x21`.
5. `FUN_cb40` / `FUN_103ea`: brightness, contrast, saturation and hue. Defaults are 0x80, 0x80, 0x80, 0x81, 0x20 at `dev+8..0xc`.

### Stop = FUN_cf6c + FUN_d413 + FUN_ad06
Stop mirrors start with `b1:0x24 = 0x40` and five bytes from DAT_33158 (zeros in file). For x535, `FUN_d413` → `FUN_1ca93` powers down: `0xC1` wValue=`0xC039`, then `0x4034` (GPIO 52 low). Then:
- `0xC6` len 0 (disable replay program);
- stop interrupt read (transport +0x08);
- stop the interrupt thread (+0x30).

### Replay program / change notification (FUN_ab47 → FUN_ac33, FUN_a8b8)
When the signal is stable:
1. The lib uploads, via `0xC6` wValue=100 wIndex=1, a list of 4-byte I2C ops for the firmware to poll every 100 ms. For HD60 S HDMI there are 10 entries: `55803c00 6a800f00 6b80fe00 01810700 0b82df00 0c823f00 0e820800 48826000 9b82f000 0e40809a` (LE u32 shown as bytes).
2. It arms a 1-byte interrupt read on EP 0x81.
3. When a watched value changes, the read completes. The host disarms it and runs format detection again.
4. Before any host I2C burst, `FUN_ad41` sends `0xC6` len 0 so firmware polling doesn't collide. `FUN_ad82` re-uploads the program afterwards.

**A simpler driver can skip this:** send `0xC6` len 0 once, then poll detection every ~250–500 ms.

## 4. Signal detection
- `DetectVideoFormat` → `FUN_8e56` → `FUN_dece` → `FUN_12a2f`. The HDMI path is a 2.3k-line MST3367 timing measurement with tables at DAT_2c7f0..
- It fills the format struct at `dev+0x4160`: +0x30 width, +0x34 active lines (per field when interlaced), +0x38 rate, +0x3c 1001-flag.
- Reported fps = `rate*(1001-flag)/1001` (`FUN_90bc`).
- Interlaced is reported as 1920×540, 720×240 or 720×288; the caller doubles the height and sets the interlaced flag.
- Mode index: `FUN_1d3d4(input, w, h, rate)` → CEA-like code, 'D' (0x44) = none.
- No signal: detection leaves `dev+0x1c = 0` and the mode index is 'D'. (`0x9A` reg `0x0E` bit7, listed here before, is the transmitter's interrupt-pending bit; see §6.) Audio rate is fixed at 48000 (`dev+0x18`).

## 5. Stream format on EP 0x83 (FUN_d476, called from ParseInput → FUN_da2e)
The payload is a stream of 32-bit words. Transfers are concatenated; packet boundaries carry no meaning.

- **Timing code** `FF 00 00 XY`, BT.656 style: `XY & 0x40` = F (field), `XY & 0x20` = V (vertical blanking). Each code is followed by one line segment, and the distance to the next code is measured. Elgato copies `min(len-4, stride)` bytes after **every** code while V=0, without checking H.
- **Audio packet** `FF 00 FF NN`, followed by `NN×4` bytes: 16-bit stereo LE PCM, 48 kHz. Elgato hands audio out in 10 ms blocks (1920 bytes).
- **Active video:** each line is `width×2` bytes of 8-bit 4:2:2 YCbCr. BT.656 order Cb Y Cr Y means UYVY / `2vuy`. A frame is `height × width×2` bytes.
- **Frame/field logic:**
  - On a V 1→0 edge, shift F into an 8-bit history `h = h<<1 | F`.
  - `h ∈ {0x00,0xFF}` means progressive: write lines sequentially from 0.
  - `h == 0xAA` means interlaced field 0: start at line 0 and step 2 lines.
  - `h == 0x55` means field 1: start at line 1 and step 2 lines.
  - On a V 0→1 edge, the frame is complete if progressive or after the field-1 (0x55) pass.
- Elgato buffers are 0x546000 bytes each (4 rotating).
- An audio-presence counter saturates at 350000 consecutive packets (`state[0x15]`).

## 6. HDMI passthrough: IT66121 transmitter (FUN_1d10a)

Recovered statically from `libUB530.dylib`; the transmitter part matches the structure of ITE's IT66121 reference driver, so register names below follow ITE's. Nothing here has been written to hardware.

### 6.1 Overview
- The MST3367 output bus feeds both the FX3 (capture) and an ITE IT66121 at I2C 0x9A, which drives HDMI out. Passthrough means bringing the IT66121 up and keeping it in step with the input.
- Transmitter object: `tx = fmt + 0x10f8` (`fmt = dev+0x4160`), with `tx+0x1c8 = dev`.
- `FUN_1d10a(tx, mode)` is the only entry point. Callers:
  - `FUN_8e56` (`DetectVideoFormat`) on every detection poll: `mode = FUN_1d3d4(input, w, h, rate)`, or 0x44 when `dev+0x1c == 0` (no lock).
  - `FUN_1d02e` (Rx init), `FUN_cc7e` (start) and `FUN_cf6c` (stop) with 0x44.
- Elgato polls only while the replay program reports a change (`FUN_ab47`). The program's last entry `0e 40 80 9a` watches 0x9A reg 0x0E bit7, so a TV hotplug wakes the host. A driver without the replay program just calls the state machine on each detection poll.
- `FUN_1d10a` returns at once if no transmitter was found (`tx+0x12 == 0`).

### 6.2 Access (no new request types)
Everything goes through the existing MCU bridge proxy (§2). Every transmitter access is bRequest 0xC0 with wValue 0x5066:

| operation | wire | `src/device.c` |
|---|---|---|
| read reg `r` | OUT `[9B 01 r]`, then IN 1 byte | `i2c_read(d, 0x9a, r)` |
| write reg `r` = `v` | OUT `[9A r v]` | `i2c_write(d, 0x9a, r, v)` |
| burst read `n` from `r` (`FUN_babb`) | OUT `[9B n r]`, then IN `n` | `bridge_read(d, 0x9a, &r, 1, buf, n)` |
| burst write (`FUN_baa4`) | OUT `[9A r v0 v1 …]` | `bridge_write(d, 0x9a, …)` |

- Bank select is reg 0x0F bit0. `b1:xx` below means write 0x0F = 1, access `xx`, then write 0x0F = 0, as Elgato does.
- `rmw(r, mask, val)` below is `FUN_1f268`: `r = (r & ~mask) | val`.
- Register names (ITE): 0x04 SW_RST (bit5 REF, bit4 AREF, bit3 video, bit2 audio, bit1 HDMI, bit0 HDCP), 0x05 INT_CTRL, 0x06–0x08 INT_STAT1–3, 0x09–0x0B INT_MASK1–3, 0x0C/0x0D INT_CLR, 0x0E SYS_STATUS (bit7 interrupt, bit6 HPD, bit5 Rx sense, bit4 video stable, bit0 interrupt-clear pulse), 0x10–0x17 DDC master (0x16 status: bit7 done, bits 5/3 error; 0x17 FIFO), 0x61–0x68 AFE, 0x70 input mode, 0x72–0x87 colour-space converter, 0xC0 HDMI/DVI, 0xC1 AV mute, 0xC6/0xC9–0xD0 packet enables, 0xE0–0xE4 audio input.

### 6.3 Chip detect and init (FUN_1db0a, FUN_1d980)
Run from `FUN_1d02e` once, and again by `FUN_1d10a` whenever reg 0x09 ≠ 0xB2 (the transmitter lost its init, e.g. after a power cycle).
1. Read regs 0x01, 0x02, 0x03, 0x05.
   - `49 12 16`: type 2 (IT66121). **This unit** (confirmed on hardware).
   - `CA 11 16` with reg 0x05 bit5: type 1, another ITE part on other boards.
   - Anything else: no transmitter.
2. State := 0. 0x05 = 0x00.
3. 0x04 = 0x3D (all resets), sleep 5 ms, 0x04 = 0x1D (release REF only).
4. 0x61 = 0x30 (AFE off).
5. 0x09 = 0xB2, 0x0A = 0xF8, 0x0B = 0x37 (interrupt masks; 0x09 = 0xB2 doubles as the "initialised" marker).
6. 0xC9–0xD0 = 0x00 (all packet generators off).
7. `FUN_20a4e`: load the 0xD4 table (§6.8).

### 6.4 FUN_1d10a(tx, mode) per call
Mode codes come from `FUN_1d3d4` (HDMI input):

| code | input | VIC sent |
|---|---|---|
| 0x00 / 0x01 | 720x240@60 / 720x288@50 (480i / 576i) | 6 / 21 |
| 0x02 / 0x03 | 1280x720@60 / @50 | 4 / 19 |
| 0x07 / 0x08 | 1920x540@60 / @50 (1080i) | 5 / 20 |
| 0x09 / 0x0A / 0x0B | 1920x1080@30 / @25 / @24 | 34 / 33 / 32 |
| 0x0E / 0x0F | 1920x1080@60 / @50 | 16 / 31 |
| 0x10 / 0x11 | 720x480@60 / 720x576@50 | 2 / 17 |
| 0x12 | 640x480@60 | 1 |
| 0x13–0x3A | PC modes (800x600 … 1440x900) | 32 (default) |
| 0x42 'B' | signal with unknown timing | 32 (default) |
| 0x44 'D' | no signal | output blanked |
| 0x45 / 0x46 | analogue SD inputs 5/6 (not on HD60 S) | 6 / 21 |

Rate is the integer rate; 59.94 is 60 plus the 1001 flag. For an HDMI source sending an AVI InfoFrame the table VIC is replaced by the source's own (below).

Steps:
1. If reg 0x09 ≠ 0xB2: re-init (§6.3), then **blank**.
2. If mode is 0x43 or 0x44, **blank**: clear the embedded-sync flags (re-running video setup §6.6 if they were set), `cur_mode` := 0x44, AV mute (0x0F = 0, 0xC1 = 1, 0xC6 = 3), service interrupts (§6.5), return. The state is not touched and the AFE stays as it was.
3. If mode ≠ `cur_mode`:
   1. `FUN_1e230`: is the receiver stable? HDMI (MST b0:0x51 bit7): b0:0x55 & 0x3C == 0x3C; it also sets `tx+2` (HDMI source with AVI InfoFrame) from b1:0x01 bit2. DVI: b0:0x14 bit7, or b0:0x15 bit6 with b0:0x14 bit4 clear. Not stable: return and retry on the next poll.
   2. AV mute; `cur_mode` := mode.
   3. **MST3367 writes for the new mode** (receiver, not transmitter; Elgato runs these during capture even with no TV):
      - `FUN_20b4c`: b0:0xB2 &= ~0x08; b0:0xB5 &= 0xC3.
      - `FUN_20c02`: b0:0x03 = 0x08 (codes 0, 1), 0x40 (2, 3), 0xC8 (0x0E, 0x0F), 0x48 (0x10, 0x11), else 0xC0.
      - `FUN_20cdc`: b0:0x0F \|= 0x20; b0:0x12 = 0x04; b0:0x17 \|= 0x02; then codes < 0x10: b0:0x12 = 0x04 (codes 0, 1) or 0x00, b0:0x13 = 0x14; codes 0x10/0x11: b0:0x12 = 0x04, b0:0x13 = 0x14; codes ≥ 0x12: b0:0x13 = 0x04.
      - b0:0x60 &= ~0x04.
   4. `FUN_2041c`: measure the source audio rate from MST b2:0x11/0x12 and b2:0x40–0x47 (N/CTS), and reprogram 0xD4 (§6.8).
   5. `FUN_1caf4`: board audio routing (the driver's `select_hdmi_audio`).
4. VIC from the table above; if `tx+2`, wait for MST b2:0x0B bit3 (≤ 100 × 5 ms) and use b2:0x4B & 0x7F.
5. Sync: separate syncs for HDMI; embedded sync with 2x CCIR656 clock only for the analogue codes. If that changes, re-run video setup (§6.6).
6. Up to 21 times: service interrupts (§6.5), run one state step (§6.6), then the mode check (`FUN_1e0d4`: in state 6, if mode or VIC differ from what is being sent, go to state 4). Stop when the state is 0 (no TV) or 6 (running).

### 6.5 Interrupt service (FUN_1dbe2)
Only when 0x0E bit7 is set:
- 0x06 bit7 (audio FIFO overflow): `tx+8` := 3 (an audio flag nothing else in the transmitter code reads).
- 0x06 bit4 (DDC FIFO error): 0x10 = 1, 0x15 = 0x09 (clear FIFO).
- 0x06 bit2 (DDC bus hang): abort DDC (`FUN_1df04`); if HDCP is on, redo HDCP.
- 0x06 bit0 (**hotplug**): HPD = 0x0E bit6. Unplugged: 0x04 = 0x1D, 0x61 = 0x30 (AFE off). State := HPD ? 1 : 0.
- 0x07 bit1 (HDCP authenticated): 0x0A \|= 0x02. 0x07 bit0 (HDCP failed): abort DDC.
- 0x08 bit4 (video-stable change): if 0x0E bit4, state 6 redoes audio (§6.7) and state 3 goes to 5; otherwise state > 1 goes to 3.
- Clear: 0x0C, 0x0D = the bits seen; 0x0E = (0x0E & 0xFC) \| 1, then without bit0.

Abort DDC (`FUN_1df04`): save 0x04 and 0x20; 0x65 = 2; 0x20 &= ~1; 0x04 \|= 1; 0x10 = 1; 0x15 = 0x0F twice, waiting for DDC each time; 0x65 = 0.

### 6.6 States (tx+4) and FUN_1e30c

| state | meaning | action | next |
|---|---|---|---|
| 0 | idle, no TV | if an EDID was parsed: forget it, HDCP off | 1 on hotplug |
| 1 | TV plugged | read and parse the TV's EDID (below) | 2, or 0 if the EDID read fails |
| 2 | EDID known | pick output colour and the table row for the VIC (`FUN_1e81c`) | 4 |
| 3 | video not stable | as state 4 | 4 / 5 |
| 4 | program video | below | 5 if stable, else 3 |
| 5 | enable output | below | 6 |
| 6 | running | nothing; mode check may send it to 4 | 4 |

**State 1, EDID read (`FUN_1e638`).** The transmitter's own DDC master reads the TV's EDID (slave 0xA0) on the HDMI-out port. Per 32-byte chunk (`FUN_1fed0`): 0x10 = 1 (host owns DDC), 0x15 = 0x09 (clear FIFO), 0x65 = 2, 0x11 = 0xA0, 0x12 = offset, 0x13 = count, 0x14 = segment, 0x15 = 0x03 (EDID read), poll 0x16 (≤ 200 times), read `count` bytes from 0x17. 0x65 = 0 at the end.
- Block 0 must have checksum 0, header `00 FF FF FF FF FF FF 00`, and a digital input (byte 0x14 bit7) or Rx sense (0x0E bit5).
- Up to 4 extension blocks (segment `n>>1`, offset `(n&1)*0x80`). A CEA block (`02 03`, `FUN_2011a`) gives YCbCr 4:4:4 (byte 3 bit5), 4:2:2 (bit4), basic audio (bit6), the supported VICs, audio formats, and HDMI mode from the vendor block OUI 00-0C-03 (DVI otherwise).
- The EDID stays in host memory (`tx+0x138`) and is never written anywhere.
- Output colour (`tx+0x10`): 4:4:4 if supported, else 4:2:2, else RGB. Input colour (`tx+0x0f`) is always YCbCr 4:2:2.

**State 2/3/4 table row (`FUN_1e81c`).** DAT_28a10 has 37 rows `{id, VIC, pixel clock Hz, flags}` (flags bit0 = 16:9, bits 1–2 = pixel repetition, terminator VIC 0xFF). An unknown VIC uses row 0 (VIC 1). Also picks the audio format from the TV's SADs (`FUN_2033c`); on the HD60 S it is forced to 48 kHz, 2 channels, 24-bit when the 0xD4 table verified.

**State 3/4, program video.**
1. `FUN_1e8d2`:
   1. 0x04 = 0x1D. AV mute if HDMI.
   2. 0x70 = (0x70 & 0x23) \| 0x40 (YCbCr 4:2:2 input, separate syncs).
   3. Separate syncs: 0x90 = 0, 0x91–0xA3 = 0xFF (sync/DE generator off), then 0xC0 = r(0x90) \| 0x08, 0xA2 = 0xFF, 0xC0 = r(0xA3) \| 0x0F. The two 0xC0 writes look like an Elgato slip (ITE writes 0x90 and 0xA3) and are overwritten in step 5. (Embedded sync instead loads 0x90–0xA3 from DAT_28c70 by VIC.)
   4. Colour-space converter (`FUN_1effc`): 4:2:2 in to 4:2:2 or 4:4:4 out needs no matrix: 0x72 = 0x72 & 0x1C, then rmw(0x0F, 0x10, 0x10). RGB out: 0x73–0x75 = `10 80 10`, 0x76–0x87 = 18 bytes from DAT_33070 (BT.601 limited range; Elgato's input mode never selects the BT.709 or full-range tables at DAT_330b0/33050/33090), 0x72 = 3 \| (0x72 & 0x1C), rmw(0x0F, 0x10, 0).
   5. 0xC0 = HDMI ? 1 : 0.
   6. Type 2 only: b1:0x58 = HDMI ? 0x10 : 0; rmw(0xC1, 3, HDMI ? 3 : 2); rmw(0xC6, 3, HDMI ? 3 : 0); rmw(0x71, 0xFC, 0x1C).
   7. AFE (`FUN_1f2d2`), `hs` = 148.5 MHz row (VIC 16 or 31): 0x61 = 0x10; rmw(0x62, 0x90, hs ? 0x80 : 0x10); rmw(0x64, 0x89, hs ? 0x80 : 0x09); rmw(0x68, 0x10, hs ? 0x80 : 0x10); 0x04 &= 0xC5; 0x59 \|= 0x08.
2. AVI InfoFrame (`FUN_1eaf4` → `FUN_1f44a`): b1:0x58–0x65 = DB1–DB13, b1:0x5D = 0x6F − ΣDB, then 0xCD = 0x03. DB1 = 0x10 / 0x30 / 0x50 for RGB / 4:2:2 / 4:4:4; DB2 = 0x08 \| (16:9 ? 0x20 : 0x10) \| (HD row ? 0x80 BT.709 : 0x40 BT.601); DB3 = 0; DB4 = VIC; DB5 = pixel repetition. Example, 1080p60 to a 4:4:4 TV: `50 A8 00 10 00`, checksum 0x67.
3. 0x04 &= ~0x08 (release video).
4. If 0x0E bit4 (video stable): state 5. Else, unless the mode is 'D', poll up to 50 × 10 ms; if the receiver goes unstable, sleep 100 ms; either way, still unstable means state 3.

**State 5, enable output.**
1. AV mute; 0x0F = 0; 0x61 = 0x00 (AFE on).
2. HDMI TV with audio (§6.7), then `FUN_1caf4`.
3. HDCP: if the source is encrypted (`dev+0x20`, from MST b1:0x01 bit0 or b1:0x34 bit7) and `tx+2`, authenticate (`FUN_20dc0`, below); else HDCP off (`FUN_2109e`).
4. Unmute (`FUN_1ec3c` → `FUN_2067c`), unless HDCP was required and failed: 0x0F = 0, 0xC1 = 0, 0xC6 = 3, and MST b0:0xB2 bits 0–1 from the source's colour info (b0:0x55 for HDMI, b0:0x14 for DVI).
5. State 6.

**HDCP (`FUN_20dc0`)**, only for encrypted sources. Keys stay inside the IT66121; the host only reads over DDC.
1. Wait for video stable (≤ 10 reads).
2. Reset HDCP (`FUN_2144a`).
3. Up to 40 × 15 ms: DDC burst read (0x15 = 0) of the TV's BCaps/BStatus (slave 0x74, offset 0x40, 3 bytes), until the BStatus HDMI bit matches 0xC0 bit0.
4. Read the BKSV (0x74, offset 0, 5 bytes) into 0x3B–0x3F. If it has exactly 20 one bits:
   - 0x04 &= ~1;
   - generate An (0x1F = 1, 1 ms, 0x1F = 0, copy 0x30–0x37 to 0x28–0x2F);
   - 0x22 = 0, 0x20 = 1;
   - unmask and clear the auth interrupts;
   - 0x10 = 0 (HDCP owns DDC), 0x21 = 1 (start);
   - poll 0x46 bit7 / 0x07 bit0, up to 100 × 5 ms.

HDCP off (`FUN_2109e`): 0x22 = 0, 0x20 = 0, 0x04 \|= 1, 0x10 = 1, clear interrupts, abort DDC.

### 6.7 Audio out (FUN_1e034), HD60 S case: 48 kHz, 2 ch, 24-bit
1. N (`FUN_1f64e`): b1:0x33–0x35 = N (6144 = `00 18 00` for integer frame rates; 11648, or 5824 above 145 MHz, for 1001 rates), then 0xC5 = 0 (CTS measured by the chip) and 0x58 = (0x58 & 0xF3) \| 0x04.
2. Input (`FUN_1f862`): 0x0F = 0; 0x04 \|= 0x04; 0xE2 = 0xE4; 0xE3 = 0x00; 0xE4 = 0x08; 0xE0 = 0xC1; 0xE1 = 0x01.
3. Channel status: b1:0x91 = 0, 0x92 = 0, 0x93 = 0x01, 0x94–0x97 = `21 43 65 87`, 0x98 = 0x02, 0x99 = 0xDB. Then 0x04 = r(0x04) & 0x04.
4. Audio InfoFrame (`FUN_1fb78` → `FUN_1fbfc`): b1:0x68 = 0x01, 0x6B = 0x00, 0x6C = 0x00, 0x6D = 0x70 (checksum), then 0xCE = 0x03.
5. 0x04 &= ~0x04 (release audio).

**Driver (`src/tx.c`), confirmed on hardware with the Pi as source (HD60 S ELD advertises LPCM 2 ch, 32/44.1/48 kHz, 16/20/24 bit):**
- Source rate: MST b2:0x40-42 = CTS, b2:0x43-45 = N (little-endian, low 20 bits), valid only while b2:0x0b & 0x62 == 0x62 (0x7e with audio, 0x1c without; N/CTS keep stale values). fs = pixel clock x N / (128 x CTS), snapped to a standard rate. The source picks its own N (vc4 sends 5632 at 44.1 kHz), so N is never used to guess the rate.
- Output N: 4096 / 6272 / 6144 for 32 / 44.1 / 48 kHz at 27, 74.25 and 148.5 MHz; 4576 / 7007 / 6864 at 25.175 MHz. The chip measures CTS (0xC5 = 0), so 1001 clocks use the same N.
- Channel status b1:0x98 = IEC 60958 fs code (44.1 k 0, 48 k 2, 32 k 3), b1:0x99 = (~fs << 4) | 0x0B (0xFB, 0xDB, 0xCB). Audio InfoFrame is rate independent (`01 00 00 00 00`, checksum 0x70).
- Only 32, 44.1 and 48 kHz are passed: every sink with basic audio must take them. Other rates, DVI sinks and sinks without basic audio keep audio off (0xCE = 0, 0xE0 = 0).
- Audio is reprogrammed in state 5, and on a rate change while running between AV mute and unmute.

### 6.8 I2C 0xD4 (not the transmitter)
- `FUN_20a4e` (init) writes 208 bytes from DAT_29110 to 0xD4 registers 0x0000–0x00CF, one OUT `[D4 00 idx val]` each. After each one it reads back (OUT `[D5 02 00 idx]`, IN 2) and compares the second byte. All match: `tx+0x1bc = 1`.
- `FUN_2163c` then rewrites 0xD4 regs 0x2A/0x2B/0x2E/0x2F/0x39/0x01 by pixel clock (27.0/27.027/74.176/74.25/148.35/148.5 MHz) and measured source audio rate.
- `FUN_1caf4` writes reg 0x0004 = 0x80 or 0x03 when `tx+0x1bc`.
- With `tx+0x1bc` set, output audio is forced to 48 kHz. That suggests 0xD4 is an audio sample-rate converter between the receiver and the transmitter/codec.
- Not flash, firmware or EDID as far as statics show:
  - every byte is read back with no EEPROM write-cycle delay;
  - the whole table is rewritten on every Initialize and transmitter re-init;
  - registers are rewritten on every mode change.
- Hardware read (2026-11-22): every 0xD4 read returns `FF FF`, the same as the unfitted 0x88. 0xD4 is probably not fitted on this unit. Elgato's verify would then fail (`tx+0x1bc = 0`), so it never writes 0xD4 again and never forces 48 kHz.
- A driver can skip 0xD4.

### 6.9 Safety
Census of every call made from the transmitter code (0x1caf4–0x21b1e, from the disassembly):
- Only the I2C helpers (`FUN_bad2`/`bafa`/`baa4`/`babb` for 0x9A, `FUN_b98e`/`b9f4` for MST3367, `FUN_9cfa`/`9da7`/`9e04`/`9e26` for 0x94/0x88/0xD4/0xAA, `FUN_9b7a` and `FUN_1c746` for the 0xD4 bridge) and libc sleeps.
- **No** `FUN_175cc` request other than bRequest 0xC0 with wValue 0x5066 (proxy) or 0x509C (MST3367). No firmware update (`FUN_177c8`), no EDID read/write (`FUN_17990`/`FUN_1796a`, the `dev+0x41a8` flash helper), no FX3 RAM (0xA0).
- DDC traffic goes out the HDMI-out port to the TV and is read-only: commands 0x03 (EDID read), 0x00 (burst read), 0x09 (clear FIFO), 0x0F (abort). Burst write is never issued.
- Writes outside the transmitter are:
  - MST3367 registers (§6.4 step 3, §6.6 state 5 unmute);
  - board audio (`FUN_1caf4`, already sent by the driver);
  - 0xD4 (§6.8).

### 6.10 Open questions for the hardware test
1. With a TV already connected before start, does a hotplug interrupt (0x06 bit0) fire after init, or must the driver read 0x0E bit6 itself and enter state 1?
2. Are the per-mode MST3367 writes (§6.4 step 3) needed for the TV picture? The mode survey shows capture does not need them in any mode. Are they harmless to capture? Do b0:0xB2 bits 0–1 written on unmute change captured colour?
3. Is 0xD4 needed for passthrough audio, and is it volatile? Does a 44.1 kHz source capture correctly without it?
4. Does a TV without YCbCr support (RGB out, BT.601/709 matrix) show correct colour?
5. 148.5 MHz detection uses the table row, so PC modes with a high pixel clock (1680x1050 etc., VIC 32 default) get low-speed AFE settings. Do they work?
6. HDCP sources (PS5 with HDCP on): does the TV authenticate, and does capture still work? (Capture of HDCP content is expected to fail regardless.)
7. Who initialised the transmitter on this unit? (See "Confirmed on hardware": it is set up before the driver touches it.) Unplug and replug the HD60 S, run only the power-up, then read reg 0x09. A driver should not depend on the answer: run §6.3 whenever reg 0x09 ≠ 0xB2, as Elgato does.
8. Elgato's transient 0xC0 writes (§6.6): harmless to skip?

## Confirmed on hardware (0fd9:0074, PS5 at 1080p60, `src/` driver)
- Pixels are **YUY2** (Y Cb Y Cr, ffmpeg `yuyv422`), not UYVY.
- Streaming starts when iface 0 alt 4 is selected after the MST3367 start sequence; no extra request is needed. About 260 MB/s on bulk EP 0x83.
- One timing code per line, then exactly `width*2` bytes of active video. 1080p60 measures 1920x1080 at 59.94 fps from the stream itself, without porting `FUN_12a2f`.
- 0x9A is an ITE IT66121 HDMI **transmitter** (regs 1-3 = `49 12 16`), i.e. the passthrough output, not the receiver. The `FUN_1d10a` state machine drives passthrough and is not needed for 1080p60 capture, though it also carries Elgato's per-mode MST3367 writes (§6.4).
- IT66121 read-only probe (2026-11-22, no TV on HDMI out; the driver had never written 0x9A):
  - Regs 0x00–0x03 = `54 49 12 16`.
  - The chip is already set up the way Elgato's init and video setup leave it with no TV:
    - 0x09–0x0B = `B2 F8 37`;
    - 0x04 = 0x05, 0x61 = 0x10 (AFE held in reset), 0x70 = 0x40, 0x72 = 0x00;
    - 0x90 = 0x00, 0x91–0xA3 = 0xFF;
    - 0xC0 = 0x00 (DVI), 0xC1 = 0x02, 0xC6 = 0x00, 0x71 = 0x1C;
    - 0x62/0x64 set for high speed.
  - 0x0E = 0x1C: no HPD, no Rx sense, video stable. This holds straight after power-up, before any MST3367 setup, survives the GPIO 52 power-down, and nothing changes it over 4.5 s idle.
  - Either the MCU firmware initialises the transmitter, or the state is left over from an earlier Elgato session.
- I2C 0xD4 and 0x88 both read `FF`: neither is fitted on this unit.
- 0xC2 stalls on alternate opens; ignoring it (as Elgato does) is harmless.
- On this unit MST3367 b1:01 bit 2 is set, so `FUN_1caf4` takes its b2:27=0 / ADC reg 3=0xA0 / MCU `90 05 00` branch.
- Audio source (`FUN_1ce00` arg, stored at `+0x1114`) picks which 0x94 codec input pairs are muted (bit 7). Measured with PS5 game audio: source 0 = HDMI (mute 0x0e/0x0f, unmute 0x10/0x11), RMS -26 dBFS; source 1 = analogue line-in only (unmute 0x0e/0x0f, mute 0x10/0x11), the ±2 LSB ADC noise floor; 3 = both mixed; 2 and 4 also set reg 4 bit 0 and reg 7 = 0xF0 and add a DC offset. The driver defaults to 0 and takes 0, 1 or 3 (`src/audio.c`, `hd60s_set_audio`).
- Gain (`FUN_1ce18`): 0.5 dB steps, 7-bit two's complement code `steps & 0x7f` over -12 to +12 dB (Elgato app: `v = 2x + 123`, library code `(v + 5) & 0x7f`; default -6 dB = 0x74). Measured on the HDMI pair 0x10/0x11 with a -20 dBFS tone: codes 0x68, 0x74, 0x7A, 0x7F, 0x00, 0x01, 0x06, 0x0C, 0x18 gave -12.05, -6.02, -2.97, -0.50, 0, +0.52, +3.05, +6.02, +12.04 dB.
- With the receiver's DVI flag set (this unit with the Pi) gain goes into the selected pair's low 7 bits and 0x0A-0x0D are 0. Without it (`FUN_1ce18`'s other branch, reg 3 bit 0) the pair keeps its own gain and a/b (0x0A/0x0B, steps > -1) or c/d (0x0C/0x0D, otherwise) get the code; Elgato does nothing for source 0 there. The driver applies gain to the analogue input only: Elgato's DVI-branch write of -6 dB to the HDMI pair would lower HDMI capture by 6 dB (measured), and its UI offers the slider for analogue audio only.
- Mute is bit 7 of the pair's two registers. The driver sets it on every pair not selected, and on all of them for the hardware mute.
- Routing (`FUN_1caf4`) depends on MST3367 b0:0x51 bit 7 and b1:0x01 bit 2 (DVI flag): it also sets b2:0x27, codec reg 3 (0xA0/0xA1) and MCU `90 05/03`. Starting with the source blanked leaves the HDMI branch selected and captures digital silence once the source appears; the driver re-runs routing whenever the flag changes (polled once a second). Measured: old driver silent for 13 s after the source came up, new driver audio after about 2 s.
- Audio is 16-bit little-endian stereo at 48 kHz, band-limited to about 18 kHz; 10 s of capture gives 48.1k frames/s against the 59.94 fps video clock.
- Every few hundred frames one line arrives `width*2 + 552` bytes long: its EAV comes through corrupted (`ff 80 ff ff 00 00 00 00 9d 9d`), so the device doesn't strip it and the horizontal blanking (`10 80…`) follows the intact video. Elgato copies the first `width*2` bytes but its fixed-distance jump then desyncs and the frame is dropped. Ours keeps the frame with the first `width*2` bytes of that line, as long as the line is under `2*width*2`; longer means a lost SAV merged two lines, so the frame is dropped.

## Mode survey (Raspberry Pi 4 KMS source, `hd60s` CLI, no driver changes)
Every mode the Pi's EDID offers was driven with `kmstest` (SMPTE pattern) and captured with `hd60s info` and `hd60s capture -n 20`. **All 20 timings produce frames with the current driver. No `FUN_12a2f` / `FUN_122da` register writes are needed**: the MST3367 start sequence from §3 plus the stream parser is enough, and no mode showed discarded frames or long lines in steady state.

| source mode | reported by `info` | stream line counts (active / blank) |
|---|---|---|
| 1080p 60, 59.94, 50, 30, 29.97, 25 | 1920x1080p, rate within 0.1 fps | 1080 / 45 |
| 1080i 60, 59.94, 50 (both 74.25 MHz and 72 MHz 50 Hz timings) | 1920x1080i at half the field rate (30.0, 29.97, 25.0 fps) | 540 per field / 22 or 23 |
| 720p 60, 59.94, 50 | 1280x720p | 720 / 30 |
| 576p 50 | 720x576p | 576 / 49 |
| 576i 50 | 720x576i, 25 fps | 288 per field / 24 or 25 |
| 480p 60, 59.94 | 720x480p | 480 / (not traced) |
| 480i 60, 59.94 | 720x480i, 30 fps | 240 per field / 22 or 23 |
| 1440x480i 59.94 | 1440x480i, 30 fps | 240 per field / 22 or 23 |

- Size comes from the stream itself: width = bytes between timing codes / 2, height = lines in the active region. 720-wide SD stays 720 wide (the Pi's pixel-doubled 13.5 MHz modes arrive as 720); 1440x480i arrives 1440 wide.
- Measured rates over 20 frames are only good to about +-1 fps for SD and 720p. The device cannot tell 60 from 59.94 (or 30 from 29.97) from the stream; both read as 60.0 +- 0.1. A consumer needing the 1001 flag has to port `FUN_12a2f` or guess.
- **Interlaced layout.** Fields alternate in the stream: `V` goes high for the vertical blanking (22-25 lines), `F` flips 3 lines into the blanking, then a full field of lines follows. The parser reads F at the first active line. F=0 carries the even frame lines (0, 2, ...), F=1 the odd lines. With a moving source (`kmstest --flip`, bar moving 8 px per field) the F=1 field is 8 px further along than F=0, so **F=0 (even lines) is first in time and F=1 completes the frame**, for 1080i, 576i and 480i alike. Same at 50 and 60 Hz. Each frame the parser emits is a woven pair of fields, so 1080i50 delivers 25 frames per second, not 50 fields.
- **Colour matrix.** `hd60s_start` applies BT.709, as the Elgato app does before the mode is known. `hd60s_stream` re-runs `colour_convert` with BT.601 once frames of 720x480, 720x576 or 1440x480 arrive and back to 709 for 720p/1080p (runt sizes during a switch are ignored). Measured SMPTE green bar Y/Cb/Cr: 146/146/46 in 1080p (709), 131/155/46 in 576p (601); the camera's output RGB matches across SD and HD.
- **Aspect.** The source's AVI InfoFrame is readable from MST3367 bank 2: 0x0B bit3 = received, 0x49 (DB2) bits 5:4 = 1 for 4:3, 2 for 16:9, 0x4B = VIC. Measured on the Pi: 576p 0x49 = 0x28, VIC 18 (16:9); 480p 0x49 = 0x18, VIC 2 (4:3). `hd60s_stream` polls it once a second into `parser.wide`; the camera fills the frame for a 16:9 SD source and pillarboxes otherwise.
- **Mode changes while streaming** are survived: the parser re-locks on the new size within a second (1080p60 -> 720p50 -> 576i50 -> 1080i60 -> 1080p60 tested). During the switch it emits a few runt frames of wrong height (e.g. 1280x12, 1280x703, 1920x1045) and one wrong-width frame, so consumers should gate on a size they have seen stable for a few frames. `hd60s` has no signal-loss indicator beyond "no frames arrive".
- 50 Hz modes behave like 60 Hz apart from the frame period and longer horizontal blanking (1080p50 line is 2640 clocks, not 2200). No 50 Hz-specific handling is needed; audio stays 48 kHz and flows in every mode.

## Alternative (no port)
`libUB530.dylib` depends only on libc++, CoreFoundation and Foundation, and has a clean `UB530_Public` API plus a pluggable transport. An x86_64 helper process under Rosetta could:
1. `dlopen` it;
2. implement the 7-slot `UB530_Transport` vtable over libusb or IOKit;
3. ship frames to an arm64 camera extension.

Rosetta's lifetime on macOS limits this approach.
