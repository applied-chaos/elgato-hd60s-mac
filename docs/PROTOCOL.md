# Elgato HD60 S (0fd9:0074) USB protocol

Recovered statically from Elgato Game Capture HD 2.11.14 for macOS
(`Game_Capture_HD_2.11.14.zip`, sha256 `e00efce3…c1ba74`). Nothing was run and no command was sent to the device.

- `Contents/Frameworks/libUB530.dylib` (sha256 `8a5c35d4…6d3e`, x86_64): the whole HD60 S device driver. It was licensed from YUAN High-Tech: the code also matches VID 0x1164 / PID 0x053x and 0x05ca:0x0901. It talks to the device only through an app-supplied `UB530_Transport` interface.
- `Contents/MacOS/Game Capture HD`: implements `UB530_Transport` as `BeddoRTUSBInterface` (IOKit) and runs the bulk/isoch readers (`CUSBMultiReaderBulkBeddoRT`, `CUSBMultiReaderIsochBeddoRT`).
- `BeddoLibrary.dylib` covers the older HD60 and Game Capture HD (Fujitsu chips). It is **not** used for the HD60 S.

Addresses below are `libUB530.dylib` file/VM offsets unless prefixed `app:`. Full Ghidra output is in `docs/re/libUB530_ghidra.c`, generated by `docs/re/DumpAll.java`. It is derived from Elgato's binary, so keep it private.

## 1. Device matching and firmware

**The app remaps IDs before handing them to the library** (app:0x100344dd0–0x100344e4e, `BeddoRTBoard` ctor):

```
if vid == 0x0fd9 && pid in {0x4f, 0x5e, 0x74}:  vid, pid = 0x1164, 0xf535
else (e.g. 0fd9:0076):                          passed unchanged
UB530_Public(transport, vid, pid)
```

So **our 0x74 runs as 1164:f535** inside libUB530. Every `pid & 0xfff` test sees **0x535**.

`UB530_Public::UB530_Public` @0x24834 then picks the class:
- PID 0x76 uses vtable 0x2bfa8 (ctor 0x17e02), an IT680x-based board (VSTATE_* strings) with a GPIO helper at 0xca8/0xd06.
- Everything else, including 0x74→f535, uses vtable 0x2bce0 (ctor 0x8bb2): the MST3367 board.

The x535 branches that **do apply to our unit**:
- `FUN_d118` jumps to LAB_d2f8 and runs `FUN_1c910` (GPIO power-up + MCU bridge probe), then `FUN_1d02e` (Rx init).
- `FUN_c8d2` also runs `FUN_1d02e`.
- `FUN_a1d0` returns true.

When the probe in `FUN_1c910` answers, `dev+0xac = 1`. **From then on every I2C access goes through the MCU bridge (`FUN_1c746`), not plain 0xC0**; see §2. That is why a plain `0xC0` read with wValue=addr returns a stale EP0 buffer.

The app picks firmware by `vendorID == 0x0fd9 && productID == 0x76` (app:0x10039b1aa). That match means BeddoRTv4 (`ub530_v200819`). Anything else, **including 0x74**, means BeddoRT (`ub530_v170317`). bcdDevice is not consulted.

Firmware:
- `Firmware/BeddoRT/ub530_v170317.bin` and `Firmware/BeddoRTv4/ub530_v200819.bin` are Cortex-M images for the Nuvoton MCU (vector table: SP 0x20000d70).
- The path builder is app:0x10039b016 (v4 → "200819"). Upload happens only via `UB530_Public::UpdateMCUFirmware` → vtable+0xa0 → `FUN_177c8`, which reads the file and size-checks it (≤0x8000).
- **No firmware upload happens at plug-in.** The device boots its FX3 firmware from SPI flash.
- EDID read/write (`FUN_17990`/`FUN_1796a`) goes through a flash/MCU helper at `dev+0x41a8`, so it is also a flash write.

**A driver must never call the firmware-update or EDID-write paths.**

## 2. Transport and control primitives

### UB530_Transport vtable (lib calls → app `BeddoRTUSBInterface` vtable app:0x100726208)

| slot | lib wrapper | app impl | meaning |
|---|---|---|---|
| +0x00 | FUN_175cc | app:0x100344aa2 | `Control(bRequest, wIndex, wValue, buf, wLength, isOut, &done)` |
| +0x08 | FUN_1757a | app:0x100344bb8 | stop interrupt read (abort pipe) |
| +0x10 | FUN_1758c | app:0x100344b68 | arm async 1-byte read on interrupt EP 0x81 |
| +0x18 | FUN_17564 | app:0x100344c18 | armed and **not yet fired** |
| +0x20 | FUN_1754e | app:0x100344c0e | armed |
| +0x28 | – | app:0x100344cf6 | start "BeddoRT_Interrupt" thread |
| +0x30 | FUN_175ba | app:0x100344d2e | stop that thread |

The app's control implementation is app:0x100344aa2, verified in assembly. It builds an `IOUSBDevRequestTO` and calls `ControlRequestTO(pipe 0)` at interface vtable +0x128:

| struct field | value |
|---|---|
| +0 `bmRequestType` | `(~isOut<<7) \| 0x40`, i.e. 0x40 OUT / 0xC0 IN |
| +1 `bRequest` | arg (sil) |
| +2 `wValue` | arg in rcx |
| +4 `wIndex` | arg in rdx |
| +6 `wLength` | arg (r9w) |
| timeouts | 3000 ms no-data, 2000 ms completion |

The lib wrapper `FUN_175cc(dev, req, A, B, buf, len, dirIn)` swaps registers (A→rcx, B→rdx). So **wValue = A and wIndex = B**, with no byte-swapping.

- Success means IOReturn ≥ 0. The bytes-done count is ignored, so a short or stale IN can't be detected.
- There is no write-then-read inside the transport: any two-step sequence happens one layer up (§2 bridge).

### Vendor requests (census of every `FUN_175cc` call site)

| bRequest | dir | wValue | wIndex | data | use |
|---|---|---|---|---|---|
| 0xC0 | OUT/IN | 8-bit I2C addr | sub-address | bytes | direct I2C, only when `dev+0xac==0`. **Not used on 0x74**: it returns a stale buffer |
| 0xC0 | OUT | `0x5000 \| target` | 0 | bytes | **MCU bridge write** (`FUN_9b7a`) |
| 0xC0 | IN | `0x5000 \| target` | 0 | n | **MCU bridge read** (`FUN_9bcf`) |
| 0xC1 | OUT | `0x4000 \| level<<8 \| pin`; `0xC000 \| pin` = make input | 0 | – | FX3 GPIO set. Used by 0x74 power-up (§3) |
| 0xC1 | IN | pin | 0 | 1 | FX3 GPIO read |
| 0xC2 | OUT | x | 0 | – | `FUN_a601`; init sends wValue=0 |
| 0xC2 | IN | 0 | 0 | 1 | status byte (probe on 05ca:0901 / x531 only) |
| 0xC3 | – | – | – | – | PID x530 only (not HD60 S) |
| 0xC5 | OUT | period | `type \| (0xac<<8)` | 4-byte entries | upload I2C replay program, transformed format (unused on HD60 S) |
| 0xC6 | OUT | period (ms) | `type \| (0xac<<8)` | 4-byte entries | upload I2C replay program, raw. **len 0 = disable** |
| 0xC7 | OUT | 100 | 0 | – | init; sets capability bit 8 (`FUN_a6a5`) |
| 0xEC | OUT | 0 | 0 | 10 bytes | `b8 22 ?? ?? ?? P1 ?? P2 ?? ca` (`FUN_a815(P1,P2)`); init uses P1=0xC0, P2=0x00. `??` = uninitialised stack in Elgato's code |
| 0xA0 | OUT/IN | addr & 0xffff | addr >> 16 | bytes | Cypress FX3 RAM access (`FUN_9adc`/`9b0e`); **no callers**, so never use |

### MCU I2C bridge (`FUN_1c746(dev, addr, wlen, wdata, rlen, rbuf)`, used when `dev+0xac==1`, i.e. on 0x74)

The Nuvoton MCU owns the board I2C bus. The bridge uses the "0x66" proxy target, so wValue = 0x5066.

- **Read** (rlen > 0):
  1. OUT `wValue=0x5066`, data `[addr|1, rlen, wdata…]`
  2. IN `wValue=0x5066`, `rlen` bytes
- **Write** to addr ∈ {0x88, 0x98, 0x9C}: OUT `wValue=0x5000|addr`, data `wdata` (= `[sub, val…]`).
- **Write** to any other addr: OUT `wValue=0x5066`, data `[addr, wdata…]`.
- Register read `FUN_9da7` = bridge read with `wdata=[sub]`. Register write `FUN_9cfa` = bridge write with `wdata=[sub, val…]`.
- MST3367 bank access is unchanged on top of this: write `[0x00, bank]` to 0x9C, then read or write `reg`.
- MCU commands go to addr 0xAA, e.g. `[12 34 57]` (status probe), `[12 34 58]` (version), `[12 34 60]` (MCU reset, `FUN_1c8d2`). On the wire that is `AB 03 12 34 5x`, which matches the `AB 03 12` Windows traces.

### I2C devices (8-bit addresses)

| addr | device | access |
|---|---|---|
| 0x9C | MStar MST3367 HDMI receiver, banked | `ReadReg(bank,reg)` @0xb9f4 = I2C write [bank] to sub 0x00, then I2C read sub=reg. `WriteReg` @0xb98e = write [bank]→sub 0, then [val]→sub reg |
| 0x9A | MST3367 second page (status/HDCP) | `FUN_bafa`: reg 0x09 ≠ 0xB2 → chip not ready; reg 0x0E bit7 = signal/sync lost |
| 0x94 | audio codec/volume (`FUN_1ce18`, `FUN_1caf4`) | regs 3,4,7,9,0x0a–0x11 |
| 0x98 | board control/MCU | reg 0x20: bit6 = SD (240/288-line) mode, written 5 at init (HD60 S); reg 0x00/0xF0 on other boards |
| 0xAA, 0xD4 | MCU bridge (0x4f/0x5e only), audio | – |
| 0x88 | analogue decoder | internal inputs 5/6 only; unused on HD60 S |

## 3. Sequences (PID 0x74)

`UB530_Public` vtable 0x2bce0: +0x18 Initialize=0x8c80, +0x20 Uninitialize=0x8cae, +0x28 Reset=0xe56e, +0x30 DetectVideoFormat=0x90bc, +0x38 SetupForVideoFormatScanning=0x90a4, +0x40 AudioRate=0x9184, +0x98 FirmwareName=0x8dbe, +0xa8/+0xb0 EDID W/R, +0xc8/+0xd0 MST3367 W/R=0x9a36/0x9a7a, +0xd8 SetInput=0x8ce2.

### Host side (app)
1. Open the device and set configuration 1.
2. Claim iface 0 (video) and iface 1 (interrupt).
3. Choose the transfer mode. The default pref `BeddoRTUseBulk=true` (EGCInitialDefaults.plist) means **iface 0 alt 4, bulk EP 0x83**. Isochronous is alt 1–3 on EP 0x83, with 4 read buffers × 160 × bytes-per-interval.
4. Construct `UB530_Public(transport, 0x0fd9, 0x0074)`, call `CreateContext(...)`, then `Initialize()`.
5. Continuously read EP 0x83 and feed the concatenated payload to `ParseInput`.
6. Poll `DetectVideoFormat()`.

### Initialize = FUN_d118 then FUN_cc7e(dev, -1)
`FUN_d118`, as seen by the lib (id 1164:f535):
1. `0xEC` OUT, 10 bytes `b8 22 00 00 00 c0 00 00 00 ca`. Gaps were unset in Elgato's code; zeros proposed.
2. `0xC2` OUT wValue=0.
3. `0xC7` OUT wValue=100.
4. **`FUN_1c910`, power-up and MCU bridge:**
   1. `0xC1` OUT wValue=`0xC039` (GPIO 57 → input).
   2. `0xC1` OUT wValue=`0x4134` (GPIO 52 → output high: MCU/Rx enable).
   3. Every 10 ms, at most 100×: `0xC1` IN wValue=`0x0039` len 1, until it reads `0x01` (MCU ready).
   4. Up to 200×: bridge read addr 0xAA, wdata `[12 34 57]`, rlen 3. That is OUT 0x5066 `AB 03 12 34 57`, then IN 0x5066 ×3.
      - `51 10 xx` ('Q',0x10): bridge OK, set `dev+0xac=1`. Then the same read with `[12 34 58]` gives the firmware version, stored as `b0<<16|b1<<8|b2` at `dev+0xc0`.
      - `33 44 55` ('3','D','U'): MCU busy. Sleep 100 ms and retry.
      - Anything else: no bridge, `dev+0xac=0`.
5. **`FUN_1d02e`, Rx init:**
   1. Read 0x9A regs 1, 2, 3, 5.
   2. Run `FUN_1db0a` and `FUN_20a4e` (MST3367 init, once).
   3. `FUN_1d10a(rx, 0x44)`.
6. `0xC6` OUT wValue=0 wIndex=0 len=0. This probes support and disables any replay program.
7. `FUN_c8d2(dev, input, -, audio, -, 0)`, which:
   - selects the HDMI input (`FUN_10e8a`, MST3367 setup);
   - calls `FUN_1ce00` (audio source);
   - writes I2C 0x98 reg 0x20 = 0x05.

`FUN_cc7e` (start):
1. `FUN_1d10a(rx, 0x44)` resets the Rx state machine (0x44 = "no mode").
2. MST3367 writes: `b0:0xAB |= 0x80`; `b2:0x27 = 0xFF`; `b0:0xB3 = 0xFF`; `b1:0x24 = 0x41`; `b1:0x25 = 0`; `b1:0x26 = 0`; `b1:0x27 = 0` ×5. Then restore 0xAB (bit7 clear) and `b2:0x27`, and set `b0:0xB3 = 0`.
3. Poll `b2:0x0E & 7` (10 × 5 ms), then write-back-to-clear `b2:0x0E` until `&7 == 0` (≤500 × 5 ms).
4. `FUN_10b6b`: colour-space conversion. `b0:0x90 = 0x15`, `0x91 = 0x15`, `0x92 = mode` (0x40 or 0x62), `0x93..0xAA` = 12 big-endian s16 coefficients (BT.601 for 640/720/768 widths, else BT.709; scaled 0xDC0/0x1000 for limited range). Then `b0:0xB0 = (b0:0xB0 & 0xC2) | 0x21`.
5. `FUN_cb40` / `FUN_103ea`: brightness, contrast, saturation and hue. Defaults are 0x80, 0x80, 0x80, 0x81, 0x20 at `dev+8..0xc`.

### Stop = FUN_cf6c + FUN_d413 + FUN_ad06
Stop mirrors start with `b1:0x24 = 0x40` and five bytes from DAT_33158 (zeros in file). For x535, `FUN_d413` → `FUN_1ca93` powers down: `0xC1` wValue=`0xC039`, then `0x4034` (GPIO 52 low). Then:
- `0xC6` len 0 (disable replay program);
- stop interrupt read (transport +0x08);
- stop the interrupt thread (+0x30).

### Replay program / change notification (FUN_ab47 → FUN_ac33, FUN_a8b8)
When the signal is stable:
1. The lib uploads, via `0xC6` wValue=100 wIndex=1, a list of 4-byte I2C ops for the firmware to poll every 100 ms. For HD60 S HDMI there are 10 entries: `55803c00 6a800f00 6b80fe00 01810700 0b82df00 0c823f00 0e820800 48826000 9b82f000 0e40809a` (LE u32 shown as bytes).
2. It arms a 1-byte interrupt read on EP 0x81.
3. When a watched value changes, the read completes. The host disarms it and runs format detection again.
4. Before any host I2C burst, `FUN_ad41` sends `0xC6` len 0 so firmware polling doesn't collide. `FUN_ad82` re-uploads the program afterwards.

**A simpler driver can skip this:** send `0xC6` len 0 once, then poll detection every ~250–500 ms.

## 4. Signal detection
- `DetectVideoFormat` → `FUN_8e56` → `FUN_dece` → `FUN_12a2f`. The HDMI path is a 2.3k-line MST3367 timing measurement with tables at DAT_2c7f0..
- It fills the format struct at `dev+0x4160`: +0x30 width, +0x34 active lines (per field when interlaced), +0x38 rate, +0x3c 1001-flag.
- Reported fps = `rate*(1001-flag)/1001` (`FUN_90bc`).
- Interlaced is reported as 1920×540, 720×240 or 720×288; the caller doubles the height and sets the interlaced flag.
- Mode index: `FUN_1d3d4(input, w, h, rate)` → CEA-like code, 'D' (0x44) = none.
- No signal: `FUN_bafa(0x9A, 0x0E)` bit7 set. Audio rate is fixed at 48000 (`dev+0x18`).

## 5. Stream format on EP 0x83 (FUN_d476, called from ParseInput → FUN_da2e)
The payload is a stream of 32-bit words. Transfers are concatenated; packet boundaries carry no meaning.

- **Timing code** `FF 00 00 XY`, BT.656 style: `XY & 0x40` = F (field), `XY & 0x20` = V (vertical blanking). Each code is followed by one line segment, and the distance to the next code is measured. Elgato copies `min(len-4, stride)` bytes after **every** code while V=0, without checking H.
- **Audio packet** `FF 00 FF NN`, followed by `NN×4` bytes: 16-bit stereo LE PCM, 48 kHz. Elgato hands audio out in 10 ms blocks (1920 bytes).
- **Active video:** each line is `width×2` bytes of 8-bit 4:2:2 YCbCr. BT.656 order Cb Y Cr Y means UYVY / `2vuy`. A frame is `height × width×2` bytes.
- **Frame/field logic:**
  - On a V 1→0 edge, shift F into an 8-bit history `h = h<<1 | F`.
  - `h ∈ {0x00,0xFF}` means progressive: write lines sequentially from 0.
  - `h == 0xAA` means interlaced field 0: start at line 0 and step 2 lines.
  - `h == 0x55` means field 1: start at line 1 and step 2 lines.
  - On a V 0→1 edge, the frame is complete if progressive or after the field-1 (0x55) pass.
- Elgato buffers are 0x546000 bytes each (4 rotating).
- An audio-presence counter saturates at 350000 consecutive packets (`state[0x15]`).

## Confirmed on hardware (0fd9:0074, PS5 at 1080p60, `src/` driver)
- Pixels are **YUY2** (Y Cb Y Cr, ffmpeg `yuyv422`), not UYVY.
- Streaming starts when iface 0 alt 4 is selected after the MST3367 start sequence; no extra request is needed. About 260 MB/s on bulk EP 0x83.
- One timing code per line, then exactly `width*2` bytes of active video. 1080p60 measures 1920x1080 at 59.94 fps from the stream itself, without porting `FUN_12a2f`.
- 0x9A is an ITE IT66121 HDMI **transmitter** (regs 1-3 = `49 12 16`), i.e. the passthrough output, not the receiver. The `FUN_1d10a` state machine drives passthrough and is not needed for capture.
- 0xC2 stalls on alternate opens; ignoring it (as Elgato does) is harmless.
- On this unit MST3367 b1:01 bit 2 is set, so `FUN_1caf4` takes its b2:27=0 / ADC reg 3=0xA0 / MCU `90 05 00` branch.
- Audio source (`FUN_1ce00` arg, stored at `+0x1114`) picks which 0x94 codec input pairs are muted (bit 7). Measured with PS5 game audio: source 0 = HDMI (mute 0x0e/0x0f, unmute 0x10/0x11), RMS -26 dBFS; source 1 = analogue line-in only (unmute 0x0e/0x0f, mute 0x10/0x11), the ±2 LSB ADC noise floor; 3 = both mixed; 2 and 4 also set reg 4 bit 0 and reg 7 = 0xF0 and add a DC offset. The driver uses 0.
- Audio is 16-bit little-endian stereo at 48 kHz, band-limited to about 18 kHz; 10 s of capture gives 48.1k frames/s against the 59.94 fps video clock.

## Unknown / unverified
- Audio channel order (left first) is assumed from I2S convention, not tested with a one-sided signal.
- 0xEC padding bytes and the meaning of 0xEC, 0xC2 and 0xC7. Possibly LED/clock/enable.
- Modes other than 1080p60 (720p, 1080i, SD), and whether `FUN_12a2f`/`FUN_122da` register writes (e.g. b0:0x11) are needed for them. SD modes also want the BT.601 matrix.
- Passthrough: the IT66121 is not initialised by the new driver.
- Isoch alt 1–3 packet sizing.
- GPIO pin semantics (52 = enable, 57 = ready) are inferred from usage only.
- Whether the app auto-prompts firmware updates. The version check is not traced.

## Alternative (no port)
`libUB530.dylib` depends only on libc++, CoreFoundation and Foundation, and has a clean `UB530_Public` API plus a pluggable transport. An x86_64 helper process under Rosetta could:
1. `dlopen` it;
2. implement the 7-slot `UB530_Transport` vtable over libusb or IOKit;
3. ship frames to an arm64 camera extension.

Rosetta's lifetime on macOS limits this approach.
